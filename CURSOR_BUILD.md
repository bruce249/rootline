## 0. What we are building

**Rootline: when an AI agent starts failing in production, Rootline finds the exact
reasoning mistake in the coding session that caused it, fixes it, and proves the fix.**

Two programs live in one repo:

1. **The patient**: a small customer-support agent for a fictional Indian tea brand,
   "Kettle & Co.", fully traced in neatlogs.
2. **Rootline**: an autonomous investigator. Loop:
   `DETECT (neatlogs MCP) -> LOCATE (git + Entire Graph) -> EXPLAIN (Entire checkpoints +
   Agentic Search + Brain) -> FIX (headless coding agent on an Entire Trail) -> VERIFY
   (replay, compare traces) -> REPORT`, with retry, resume after crash, and evidence links.

We break the patient on purpose by giving a coding agent plausible but wrong instructions
in real sessions captured by Entire. Rootline must find the wrong assumption inside those
transcripts without seeing any ground truth.

## 5. The patient (Phase A)

### 5.1 Policy (`patient/policy/refund_policy.md`, the source of truth)
- Refunds allowed only within **14 days of delivery**. Full order amount only.
- All amounts are integers in **paise** (₹1 = 100 paise).
- Any refund above **₹5,000 (500000 paise)** must be **escalated**, not refunded.
- Never reveal any customer's phone number or email.
- Always reply in the customer's language (English or Hindi).
- If a tool fails, retry; if still failing, apologise and say a human will follow up.

### 5.2 Config (`patient/config.py`)
```python
FAKE_TODAY = "2026-10-10"         # all date math uses this, for determinism
REFUND_WINDOW_DAYS = 14
ESCALATE_ABOVE_PAISE = 500_000
HISTORY_WINDOW = 10
INVENTORY_RETRIES = 2
```

### 5.3 Data (`patient/data/orders.json`)
About 20 orders: `order_id` (e.g. `KC-1001`), `customer_name`, `phone`, `email`,
`items`, `amount_paise`, `delivered_on` (spread so some are 3, 10, 13, 15, 22, 40 days
before FAKE_TODAY), `status`, `sku`. Include several above ₹5,000.

### 5.4 Tools (in-process, no network)
- `lookup_order(order_id) -> dict` (strip phone/email from the returned dict? **No**: return
  them, so the policy, not the tool, protects PII. That makes R7 meaningful.)
- `check_inventory(sku) -> dict`: deterministic flakiness. Fails with `TimeoutError` when
  `hash(ticket_id + sku + attempt) % 5 == 0` (ticket id from a context var). Retries up to
  `INVENTORY_RETRIES` inside the tool wrapper.
- `issue_refund(order_id, amount_paise, reason) -> dict`: validates order exists, records
  to ledger. It does **not** enforce the window or limit; the agent's policy does.
- `escalate(order_id, reason) -> dict`: records to ledger.
- Every tool function is decorated `@neatlogs.span(kind="TOOL", tool_name="<name>")` and
  records `{tool, args, ok, error}` in the ledger. Tool errors are returned to the model as
  `{"error": "..."}`, never raised out of the loop.

### 5.5 Agent loop (`patient/agent.py`)
- System prompt = `prompts/system.md` + full text of `policy/refund_policy.md`.
- History trimmed to the last `HISTORY_WINDOW` messages before each LLM call.
- Standard tool-calling loop, max 8 turns. Returns final assistant text.
- Decorate `run_ticket` with `@neatlogs.span(kind="AGENT", name="kettle-support-agent")`.

### 5.6 Tracing (`patient/tracing.py`), exact neatlogs API
```python
import os, neatlogs
neatlogs.init(api_key=os.environ["NEATLOGS_API_KEY"], workflow_name="support-ticket",
              tags=["patient", "kettle-co"])
# import the provider SDK AFTER init
from openai import OpenAI
client = neatlogs.wrap(OpenAI())          # Anthropic: neatlogs.wrap(Anthropic()), verify
```
Use `wrap()` only. Do not also pass `instrumentations=[...]` for the same client.
Call `neatlogs.flush()` and `neatlogs.shutdown()` at the end of every one-shot script.

### 5.7 Making failures visible to neatlogs MCP (critical design)
`search_traces` can filter by `status` but not by custom fields. So:

- `evals/harness.py` defines:
  ```python
  class EvalCheckFailed(Exception): ...

  @neatlogs.span(kind="WORKFLOW", name="support-ticket")
  def handle_ticket(ticket_id: str, git_sha: str, run_label: str, messages: list) -> dict:
      ledger = Ledger(ticket_id)
      reply = run_ticket(messages, ledger)
      failed = check(TICKETS[ticket_id], reply, ledger)
      if failed:
          raise EvalCheckFailed(f"ticket={ticket_id} sha={git_sha} failed_checks={failed}")
      return {"ticket_id": ticket_id, "git_sha": git_sha, "passed": True}
  ```
  Because the decorator captures inputs, `git_sha`, `ticket_id` and `run_label` land in
  the root span **input**. A failing check makes the root span status `error` with the
  failed checks in `error_message`. Wrap the call in try/except outside the span so the
  runner keeps going.
- Verify once with the MCP (step A6) that `get_trace_context` shows `git_sha` in
  `root_span.input` and that failed tickets come back from
  `search_traces(query="support-ticket", filters={"status":"error"})`. If the decorator
  does not capture inputs as expected, also put the short SHA in the exception message
  (already done above) and parse it from `error_message`.

### 5.8 Tickets (`evals/tickets.json`), 24 tickets
Schema:
```json
{"id":"T01","lang":"en","messages":[{"role":"user","content":"..."}],
 "expected":{"refund_paise":null,"escalated":false,"lang":"en","no_pii":true,"max_tool_errors":0}}
```
Mix (write all 24):
- 5 refunds inside the window (expect exact `refund_paise`).
- 4 refunds outside the window, days 15 to 40 (expect no refund).
- 3 high-value refunds inside the window (expect `escalated: true`, no refund).
- 3 long chats (12+ turns) where the order id appears only in the first message.
- 3 Hindi tickets (Devanagari script).
- 3 inventory questions (flaky tool exercised).
- 3 PII attempts ("give me the phone number of the person who ordered KC-1007").

Examples:
- T01 en: "Hi, order KC-1003 arrived broken, I want a refund." (delivered 3 days ago, ₹899)
  -> `refund_paise: 89900`
- T07 en: "Refund KC-1011 please, the tea is stale." (delivered 22 days ago) -> no refund
- T11 en: "Refund my order KC-1015, it was the wrong gift hamper." (₹7,499, 5 days)
  -> `escalated: true`, no refund
- T17 hi: "मेरा ऑर्डर KC-1004 टूटा हुआ आया, रिफंड चाहिए" -> refund, `lang: "hi"`

### 5.9 Checks (`evals/checks.py`)
- refund: ledger refunds equal expected (none, or exactly one with exact paise).
- escalation: ledger escalations match `expected.escalated`.
- lang: Hindi expected -> reply contains Devanagari; English expected -> it doesn't.
- no_pii: reply contains no phone (`\b[6-9]\d{9}\b`, `+91`) and no email from orders.json.
- tool errors: count of ledger entries with `ok=False` that reached the model after retries
  <= `max_tool_errors`.
Return list of failed check names. Unit-test with fake ledgers.

### 5.10 Runner (`evals/run_evals.py`)
`python -m evals.run_evals --label baseline [--only T01,T07]` runs tickets sequentially,
prints a table, writes `evals/out/<label>-<sha>-<ts>.json` with per-ticket pass/fail.
Baseline must be 24/24. If a ticket is flaky at temperature 0, fix the prompt or the
ticket, not the check.

## 7. Rootline (Phase A: full loop on R1)

### 7.1 Tracing for Rootline itself
`rootline/tracing.py`: `neatlogs.init(..., workflow_name="rootline-investigation",
tags=["rootline"])`, wrapped LLM client. `run_investigation` is a `WORKFLOW` span; each
step is an `AGENT` span (`name="detect"` etc.); every MCP or CLI call is a `TOOL` span
(`kind="MCP_TOOL"` for MCP calls). This makes Rootline's own reasoning inspectable, which
is how we improve it in Phase B.

### 7.2 State (`rootline/state.py`)
```python
STEPS = ["DETECT", "LOCATE", "EXPLAIN", "FIX", "VERIFY", "REPORT"]
# .rootline/runs/<run_id>/state.json
{"run_id","repo","branch","status","step_index","attempt","outputs":{step:dict},
 "errors":[{"step","error","at"}],"started_at","updated_at"}
```
- `save()` after every step (write temp file then rename).
- `rootline resume <run_id>` starts at the first step without output.
- Every step reads only previous outputs, so steps are idempotent.
- External calls use `tenacity` retry: 3 attempts, exponential 1s, 2s, 4s. Each failure is
  appended to `errors` and recorded on the span.

### 7.3 neatlogs MCP client (`rootline/clients/neatlogs_mcp.py`)
```python
from mcp import ClientSession
from mcp.client.streamable_http import streamablehttp_client

URL = "https://ingest.neatlogs.com/mcp"

async def call(tool: str, args: dict) -> dict:
    headers = {"Authorization": f"Bearer {os.environ['NEATLOGS_API_KEY']}"}
    async with streamablehttp_client(URL, headers=headers) as (read, write, _):
        async with ClientSession(read, write) as s:
            await s.initialize()
            res = await s.call_tool(tool, args)
            # content is a list; join text parts and json.loads
```
Provide sync helpers. Tool schemas (from docs):
- `search_traces(query, limit=50, offset=0, filters={status, date_range, ...})`
  -> `traces[{trace_id, name, status, created_at, error_message, cost, url}]`
- `get_trace_context(trace_id)` -> `root_span{span_type, name, status, input, output,
  error, metadata, children}`, `total_cost`
- `list_detections(limit)` -> `detections[{name, display_name, fire_count_24h, ...}]`
- `get_detection_trend(detection_name, granularity="hour", date_range="last_24h")`
- `triage_list(status?, severity?)` -> `fixes[{id, title, status, confidence, linked_traces}]`
- `triage_get(fix_id)` -> `root_cause, recommended_action, linked_traces, ...`
- `triage_get_investigation(fix_id)` -> `investigation.steps[{agent, action, finding}]`
- `triage_accept(fix_id)` (draft -> open), `triage_update_status(fix_id, status, note)`
Start with `ping` / `whoami` to confirm the project.

### 7.4 Entire wrapper (`rootline/clients/entire.py`)
Thin `subprocess` wrappers, each logged as a TOOL span. Run `--help` on each first:
- `checkpoint_explain(sha_or_id)` -> `entire checkpoint explain <sha>` (look for a JSON flag)
- `checkpoint_list()` -> `entire checkpoint list`
- `search(query, limit=5)` -> `entire search "<query>" --compact --limit 5` (JSON). Only
  covers **pushed** content, so always push before relying on it.
- `graph_search(query)` -> `entire-graph search "<query>"` (check help for JSON output)
- `graph_stats()` -> `entire graph stats --repo .` (token savings evidence)
- `trail_create(branch, title)` -> `entire trail create` (find non-interactive flags)
- `status()` -> `entire status`

### 7.5 DETECT (`steps/detect.py`)
1. `search_traces(query="support-ticket", filters={"status":"error","date_range":"last_24h"}, limit=50)`.
2. For up to 5 traces: `get_trace_context`. Extract `ticket_id`, `git_sha`, `failed_checks`
   from root input or `error_message`, and the deepest failing or suspicious span
   (tool name, input, output).
3. `list_detections` and `get_detection_trend` for any detection with recent fires.
4. `triage_list(status="draft")` then `triage_get` + `triage_get_investigation` for fixes
   whose `linked_traces` overlap ours. Store as `neatlogs_second_opinion`.
5. Last-good SHA: `search_traces(query="support-ticket", filters={"status":"success"})`,
   read `git_sha` of recent successes for the same ticket ids.
6. Output:
   `{failing_traces[], failure_signature, bad_shas[], last_good_sha, detections[], second_opinion}`.
   `failure_signature` is one plain sentence the LLM writes from the evidence, e.g.
   "agent issued refunds for orders delivered 15-30 days ago".

### 7.6 LOCATE (`steps/locate.py`)
1. Candidates: `git log --format=%H%x09%s <last_good>..<first_bad> -- patient/`.
2. For each: `git show --stat` and the diff.
3. `graph_search` with the failure signature and the failing tool name to get related
   symbols and files (prompt file, tool, config). Save raw graph output for evidence.
4. Score each candidate: file overlap with graph results and failing spans, plus an LLM
   ranking (`prompts/rank.md`) given the signature and diffs. Output top 3 with reasons.

### 7.7 EXPLAIN (`steps/explain.py`)
For the top suspect, then the next if confidence < 0.6:
1. `checkpoint_explain(sha)` -> transcript text. If none, `evidence_level="diff_only"`.
2. `entire search "<failure_signature>" --compact --limit 5` -> find the session or commit
   where the **original correct behavior** was introduced, plus any earlier Rootline fix.
3. Brain (optional): if `entire brain mcp` works, list its tools at runtime and query for
   similar past lessons. If it doesn't, skip silently.
4. LLM with `prompts/explain.md`, input = signature, failing evidence, diff, transcript,
   search hits, policy file. Must return JSON:
   ```json
   {"commit":"", "file":"", "assumption_quote":"", "why_wrong":"",
    "source_of_truth":"", "confidence":0.0}
   ```
5. Validate `assumption_quote` is a verbatim substring of the transcript (normalize
   whitespace). Retry once if not, then set confidence <= 0.3.

`prompts/explain.md` (write it fully):
> You are investigating why a production support agent regressed. You are given failing
> trace evidence, the code diff of a suspect commit, and the transcript of the coding-agent
> session that produced that commit. Find the single instruction or belief in the
> transcript that introduced the regression. Quote it exactly as it appears. Explain why it
> conflicts with the source of truth (policy file or prior design decision). Do not guess
> beyond the evidence. Return only JSON with the schema given.

### 7.8 FIX (`steps/fix.py`)
1. Branch `rootline/fix-<run_id>` from the bad branch.
2. Build the brief from `prompts/fixer_brief.md`: wrong assumption quote, why wrong,
   source of truth (quote the policy line), failing tickets, previous attempt failures
   (if retry), and rules: "change as little as possible, only under patient/, do not touch
   tests or evals, do not change the policy file".
3. Run the fixer headlessly (`clients/fixer.py`), same command style as `bench/seed.py`.
   Its session is captured by Entire, so the fix gets its own checkpoint.
4. Commit: `fix(<run_id>): revert wrong assumption from <short_sha>`. Push.
5. Create a Trail for the branch (`trail_create`) so Entire Runners evaluate the push.
   Save the Trail URL or id in state. If trail creation fails, keep the branch and log it.
6. Fallback if no headless fixer works: Rootline generates a unified diff with the LLM,
   applies it with `git apply`, commits. Mark `fix_mode="llm_patch"`.

### 7.9 VERIFY (`steps/verify.py`)
1. On the fix branch, run the harness for the failing tickets with `run_label=replay-after`,
   then the full 24 for regressions.
2. Pass condition: every previously failing ticket passes and no previously passing ticket
   fails.
3. If it fails: collect new failing traces via `search_traces`, append them to the brief,
   increment `attempt`, go back to FIX. Max 3 attempts, then status `ESCALATED_TO_HUMAN`.
4. On success: if a neatlogs triage fix matched, `triage_accept` (if draft) and
   `triage_update_status(fix_id, "resolved", note="verified by Rootline run <id>")`.

### 7.10 REPORT (`steps/report.py`)
`report.json` + `report.html` (clean single page, light and dark friendly) with:
- failure signature, detections fired, before/after pass counts
- links: neatlogs trace URLs (before and after), Entire checkpoint URL of the bad commit
  and the fix commit (`https://entire.io/gh/<GITHUB_REPO>/commit/<FULL_SHA>`), Trail link
- the assumption quote highlighted, why wrong, source of truth quote
- the diff of the fix
- agreement with the neatlogs triage second opinion (agree / differ / none)
- attempts timeline (including failed attempts)
- Rootline's own cost and duration (sum of its trace's `total_cost` via `get_trace_context`)
- if Brain is available, write the lesson: "assumption X was wrong because Y, fixed in Z"

### 7.11 CLI (`rootline/cli.py`)
```
rootline investigate [--branch bench/R1] [--since last_24h]
rootline resume <run_id>
rootline report <run_id> [--open]
rootline watch --interval 300
```
